# AIEN: mission, ownership and evidence

Use this guide when choosing an AIEN repository, explaining the project, or making a cross-repository/status claim. This is routing knowledge, not permission to publish, merge, rename repositories, access hardware or change a live service.

**Source snapshot: 2026-10-25.** Start with [the live agent entrypoint](https://www.aienos.com/agents/), [shared rules](https://www.aienos.com/agents/RULES.md) and [machine-readable catalog](https://www.aienos.com/data/agent-repos.json). The catalog read for this guide was generated at `2026-10-25T21:31:00Z`, listing 57 public repositories. It supplies actual default branches, instruction filenames, fork and archived flags. It is an hourly discovery index, not proof of implementation or deployment. Follow its linked `AGENTS.md` or `CLAUDE.md`, then the relevant directory's `.crumb` and source.

## What AIEN is trying to build

AIEN, led by Drake Stapleton with agents as collaborators, is building persistent intelligent computing on owner-controlled hardware: an operating system, an explicit computational language, a machine realization layer, a host runtime and a reproducible verification/learning loop. The ambition is a system that turns an objective into explicit conditions, discovers how the available machine can realize them, verifies effects, acts and learns from the result. It is **research-grade**, not a finished autonomous operating system or a promise of flawless verification.

Phase (2026-10-26): AienOS as a product entered **alpha testing** (phases: alpha testing, then beta, then full release). "Alpha" here is the product phase, not a model name and not Core's `aien-alpha` tag pipeline. The downloadable package is called **Sovereign Intelligence** (SI), built on AienOS: the Core engine built from `aien-sovereign-core-mv` main, the seeded Omega install wizard and `omc`, and the CUDApp user-space replacement. Its home and only download location is [aien-dev/sovereign-intelligence](https://github.com/aien-dev/sovereign-intelligence) (GitHub Releases named "Sovereign Intelligence alpha-YYYYMMDD.N", installer under `installer/`, `docs/WHAT-I-AM-BUILDING.md` holds the per-repository audit with evidence levels; install from the public repo, never a script from aienos.com: `git clone --branch alpha-20261026.2 https://github.com/aien-dev/sovereign-intelligence && cd sovereign-intelligence && sh installer/install.sh`, and `aienos.com/install.sh` is a 301 to the repo's README; page: https://www.aienos.com/alpha/). [aien-dev/AienOS-nv](https://github.com/aien-dev/AienOS-nv) is AienOS's own repository and links back to SI. The name `aien-dev/aienos` is retired by GitHub and stays a redirect to `aienux`; never point a release or link there. In copy write "Sovereign Intelligence, built on AienOS", never "AienOS is now SI". Check SI's releases before claiming a published artifact. The GPU path runs only on DGX Spark GB10 (sm_121) and nothing is QUALIFIED: the 3x physical qualification is NOT_RUN. Components testers do not receive in that bundle (for example the aienux kernel, physics-mv and research repositories) keep their own labels, which may still say pre-alpha.

Sovereign Intelligence (SI) is also the project's front door: its README maps the whole stack and indexes every public aien-dev repository by layer with its evidence level. The index is rebuilt hourly from GitHub by `index/gen/index.om`, which exits 1 and names any public repository without an entry in `index/curated.yml`. Rule: after editing any aien-dev repository's purpose, status or links, or adding a repository, update its `index/curated.yml` entry in the same piece of work. Never name a private repository there.

The short working doctrine is:

> Weights suggest. Programs explain. Omega verifies. Physics authorizes. Evidence teaches.

Read that with the [canonical responsibility boundaries](https://github.com/aien-dev/aien-architecture-mv/blob/main/PLAN_AUTHORITY.md): `ATLAS AWAKENS. ALLEN INTENDS. AIEN PROPOSES. OMEGA DEFINES. FORGE REALIZES. AEGIS VERIFIES. HARDWARE ACTS. EVIDENCE TEACHES.` These are responsibilities, not a literal turn order. FORGE is physical realization and policy, not a substitute security authority. AEGIS is the cross-cutting invariant checker, not automatically the repository named `aegis-runtime-mv`.

- **Weights/model fluency propose**, never establish truth, permission or completed work. A persuasive explanation, generated program or model review is not a measured result.
- **Programs make claims inspectable**: inputs, transformations, invariants, failure conditions and allowed effects. Omega aims to separate computational meaning from disposable machine representation. A semantic identity is not proof that a program is correct or authorized.
- **Physics constrains realizability**: memory movement, locality, bandwidth, queues, scheduling and device/OS interfaces must be established, not invented. Removing a userspace library does not establish independence from the kernel, firmware or driver.
- **Evidence teaches**: execute a declared experiment, retain failures and controls, bind observations to source, toolchain, command and environment, then distill a reusable lesson. This is experience-first learning, not turning fluent text into knowledge by storing it.
- **Omega is the forward first-party implementation language**. Existing C, Rust, shell and other infrastructure are unfinished migration, not evidence that the destination changed. Qualify replacements, migrate actual consumers and remove superseded implementation while preserving history and immutable receipts. Do not rename foreign source or alter language statistics to pretend a migration happened. External interfaces and independent oracles need explicit roles.

The default-branch [Omega README](https://github.com/aien-dev/omega-mv/blob/main/README.md) and [instructions](https://github.com/aien-dev/omega-mv/blob/main/AGENTS.md) distinguish the merged seeded `.om` compiler from legacy OSC/C and candidate-only work. The earlier M6 fixed-output self-copy result is not general compiler self-hosting. Compiler fixpoint, diverse compilation, GPU launch and end-to-end model execution are separate claims. Discover the current supported language and pins before writing `.om`; never infer them from an old model answer or skill.

omega-mv also holds `om/tls/`, a TLS 1.3 client written in seeded Omega with its own primitives (SHA-2, HMAC/HKDF, X25519, ChaCha20-Poly1305, AES-GCM, ECDSA P-256/P-384, RSA PKCS#1/PSS verify, X.509 path validation). It was merged in omega-mv #813 (`705c0f01`, 2026-10-26). Build a program against it with `sh om/tls/build.sh OMC PROGRAM.om OUT`. Its README states the side-channel limits. Route HTTPS and SMTPS needs in `.om` there, not to a host TLS library.

Omega's language and toolchain path to 1.0 is [`docs/ROADMAP-1.0.md`](https://github.com/aien-dev/omega-mv/blob/19f014f2178ca9cd3473728fe00a475a2398c409/docs/ROADMAP-1.0.md) (merged in omega-mv #801, 2026-10-26). It has an audit at `3364a1dfd` and milestones RM1..RM11, each with acceptance gates and a tracking issue, [#790](https://github.com/aien-dev/omega-mv/issues/790) through [#800](https://github.com/aien-dev/omega-mv/issues/800). It owns only that acceptance contract. Milestone IDs, status and cross-project order stay with aien-architecture below, and the RM names exist so they are not confused with its `M` rows. Route language work to the RM issue that names it and to the existing owner issue it links. An open RM item is missing work, not something Omega cannot do, and nothing in the file is a readiness claim.

## Which authority answers which question?

In [aien-architecture-mv](https://github.com/aien-dev/aien-architecture-mv):

1. [PLAN_AUTHORITY.md](https://github.com/aien-dev/aien-architecture-mv/blob/main/PLAN_AUTHORITY.md) defines precedence.
2. [doctrine/ARCHITECTURE.md](https://github.com/aien-dev/aien-architecture-mv/blob/main/doctrine/ARCHITECTURE.md) owns responsibilities and terminology.
3. [doctrine/ROADMAP.md](https://github.com/aien-dev/aien-architecture-mv/blob/main/doctrine/ROADMAP.md) owns milestone IDs and status, including historical limitations.
4. [CURRENT_EXECUTION_PLAN.md](https://github.com/aien-dev/aien-architecture-mv/blob/main/CURRENT_EXECUTION_PLAN.md) owns cross-project sequence. Read later dated corrections, not just its opening baseline.
5. [ADRs](https://github.com/aien-dev/aien-architecture-mv/tree/main/docs/adr) own recorded decisions. Check status and amendments; an ADR filename or merged prose is not implementation evidence.
6. The [capability register](https://github.com/aien-dev/aien-architecture-mv/blob/main/docs/capability-register/register.tsv) (aien-architecture-mv [#345](https://github.com/aien-dev/aien-architecture-mv/pull/345), merged 2026-10-30 as `5821a6acae2d01d998dfb2782527c16abbe604be`) is the record for CUDA-replacement capability. Each row gives the owner repository, the exact commit, the arch it ran on, an evidence level and an evidence file at that commit. `tools/capreg/capreg.om` checks it and refuses a row whose rev is not a 40-hex sha or whose evidence is not `aien-dev/<repo>@<sha>:<path>` or `register:<path>`; `AIEN_OMC=<omc 734f0a39…> sh tools/capreg/gate.sh` runs the fixtures, the register and a planted bad row, and reports NOT_RUN (exit 3) for any other compiler. Confirm each row you quote against its cited file. A register row indexes evidence; it is not evidence itself, and code and receipts still win when the two differ.

Component code and reproducible evidence win for what actually runs. Architecture wins for ownership and intended cross-project sequence. Do not create a competing master plan to resolve a contradiction; record it and repair the proper authority.

- [aien-math](https://github.com/aien-dev/aien-math) (private): a Wolfram Language replacement written in `.om`, checked against a corpus of sourced Wolfram recordings. Since main `43c629db362b48aeec3590a8f0cd30e927e5ec16` (PR #2, merged 2026-10-26) its runners fail closed: a nonzero candidate exit fails the row; comparisons in `tests/oracle_common.py` keep the whole result structure instead of matching fractional number tokens; an empty, null or malformed selected corpus prints `CORPUS FAULT` and exits nonzero; Alpha rows (`python3 tests/run_alpha.py`) and `--limit` selections print `NOT_RUN` in `tests/run.py`; and an `intentional_difference` reason excuses a mismatch only when the result equals a sourced `alternate` full answer. Quote a pass count only from a full, unlimited `tests/run.py` run with its exit status, the Alpha result and the guard controls (`python3 -m unittest discover -s tests/unit -p test_oracle_guards.py -v`). Scores from the earlier matcher are dated history and do not compare with current ones. Land changes through a pull request, draft while a dependency is pending, not by pushing to `main`.

For memory, do not route to an archived repo just because its name sounds right. ## Status discipline and known source drift

Keep **proposed**, **implemented**, **verified**, **qualified** and **deployed** separate. Report exact repository/commit, command, backend, date, verdict and exclusions. NOT_RUN, BLOCKED_HARDWARE, BLOCKED_OPERATOR and MISSING_IMPLEMENTATION never mean PASS. Host execution on a machine with a GPU is still host evidence; QEMU evidence does not qualify physical hardware; a single kernel parity test does not qualify serving a complete model. A merged PR is not a release, an open PR is not an available feature, and neither proves what binary is running.

**Merge is not Alpha.** The inspected [Omega workflow](https://github.com/aien-dev/omega-mv/blob/main/.github/workflows/aien-verification.yml) header explicitly says GitHub checks are advisory and do not gate merges, while `alpha/*` tags require a signed full Spark bundle for a commit on main. Inspect the bundle's actual backends and coverage before saying hardware-qualified. Do not generalize one repo's workflow or historical README to all merge policy; never add an automatic merge label without authority.

**Repository default-branch protection rulesets across `aien-dev`.**
- **Strict PR-only / zero-bypass (`main-protected`)**: Since 2026-10-25, `aien-dev/omega-harness` (25838607), `aien-dev/omega-bridge` (25838629) and `aien-dev/omnet` (25852242) carry an active branch ruleset named `main-protected` on default branch `main`: deletion, non-fast-forward and pull-request rules, zero required approvals, no bypass actors (`bypass_actors: []`), all three merge methods allowed, `require_extra_approval_for_unattributed_changes: false`. A direct `git push origin HEAD:refs/heads/main` fails with `GH013: Repository rule violations found ... Changes must be made through a pull request`. The zero-approval settings exist so the labeled auto-merge pipeline keeps working, not because review is unnecessary.
- **Admin-bypass PR protection (`main-protect`)**: `aien-dev/omega-mv` (25770320) and `aien-dev/aienux` (25770328) carry ruleset `main-protect`: deletion, non-fast-forward and pull-request rules, with `require_extra_approval_for_unattributed_changes: true` and an `OrganizationAdmin` bypass (`bypass_mode: "always"`).
- **Non-PR promotion protection (`main-verified-promotion`)**: `aien-dev/open-humanity` (25770331), `aien-dev/CUDApp` (25770321) and `aien-dev/aien-receipts` (25770325) carry deletion and non-fast-forward rules only, with `OrganizationAdmin` bypass.
Protection elsewhere is unmeasured rather than absent: the current token cannot read organization rulesets (`gh api orgs/aien-dev/rulesets` needs the `admin:org` scope). Never assume either state; read the live rules for the exact repository and branch before pushing: `gh api repos/aien-dev/<repo>/rules/branches/<branch>`.
